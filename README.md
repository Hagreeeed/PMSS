# Light Exposure Tracker — ЛР7

Мініпроєкт: усі модулі ЛР1–ЛР6 зібрані в одну систему моніторингу освітленості робочого місця.

Гілка `lab7-smart-system`, зроблена на основі ЛР6. Пакет `com.example.lab7`, minSdk 31.
Відкриваю цю папку в Android Studio і запускаю конфігурацію `app` на емуляторі.

## Як працює система

Кожні 50 мс:

1. Беру останнє значення датчика світла (ЛР1) і пропускаю через медіанний фільтр на 9 значень.
2. Відфільтроване значення йде у вікно з 20 точок для моделі TFLite (ЛР6).
3. Стан вважається критичним, якщо:
   - освітленість нижче 300 лк і тримається так 1 с (норма від 350 лк, між ними стан не змінюється);
   - або модель 3 рази поспіль бачить «різке затемнення» з упевненістю від 80 %, і світло при цьому нижче 70 % від максимуму у вікні. Після цього критичний стан тримається 10 с.
4. У критичному стані в режимі AUTO вмикається лампа і вібрація (ЛР4), а на Mock BLE-хаб іде `LAMP:ON` (ЛР2).
5. Кожні 2 с (0,5 с, коли освітленість змінюється) запис іде в Room (ЛР5). Події, тобто ввімкнення лампи й спрацювання правил, пишуться окремо.
6. Кожні 5 с невідправлені записи йдуть на REST-хаб (ЛР3). Запис позначається `synced` тільки після того, як сервер повернув той самий `sampleId`. Якщо мережі немає, записи чекають у Room і досилаються одразу після її появи.

Smart-сценарії налаштовуються на вкладці «Правила»: «якщо метрика > / < поріг, то дія».
Метрики: освітленість, прискорення X / Y / Z. Дії: вібрація, увімкнути лампу, сигнал `ALERT` на BLE-хаб.
За замовчуванням є правило з методички: «якщо X > 10 м/с², то вібрація».

## Структура

```
di/          AppContainer — ручне DI, створює всі залежності
domain/      логіка без Android: SmartPipeline, MedianFilter, SpikeMonitor,
             DecisionEngine, RuleEngine, LightWindow, Ports (інтерфейси), model/
data/        реалізації інтерфейсів
  device/    датчики, мережа, TFLite, вібрація й ліхтарик
  local/     Room: readings, rules
  remote/    Retrofit: POST /readings, GET /command
  repository/
  ble/       Mock BLE-хаб
ui/          екрани Compose у вигляді Contract / ViewModel / Screen:
             dashboard, analytics, rules, devices, sensors
```

Activity тільки передає `onStart` / `onStop` у `SmartPipeline`. Коли застосунок у фоні, датчики, модель, запис і опитування зупиняються. Поворот екрана роботу не перериває.

## Запуск хаба

```
python demo-hub/server.py
adb reverse tcp:8787 tcp:8787
```

Консоль хаба: http://127.0.0.1:8787/. Там видно отримані записи й кнопки для режиму REMOTE.
Адресу хаба можна змінити в `local.properties` (`hub.url=...`).

## Як перевіряв

- Critical: Virtual Sensors → Light, 600 → 150 лк. Лампа ON, `LAMP:ON` у терміналі BLE, подія в Room і на хабі.
- Хибне спрацювання: короткий викид до 20 лк (0,15 с) поглинається фільтром, на Dashboard росте лічильник викидів. Викид 0,4–0,5 с лампу теж не вмикає.
- Втрата зв'язку: `adb shell svc wifi disable` і `svc data disable`. Хмара OFFLINE, Pending росте. Після `enable` записи досилаються.
- Правило: `adb emu sensor set acceleration 12:0:5` → вібрація і подія «Правило».
